Both `scripts/jobs/library-source-drift-scan.sh` (line 95: `die "no library/sources/README.md ..."`) and `scripts/jobs/regenerate-topics-counts.sh` (line 240: `die "no library/topics in the synced clone ..."`) FATAL with a non-zero exit when the synced journal clone has no `library/` corpus. On this instance (host g9, the leader, journal tip has no `library/` directory) that makes `garden-library-source-drift-scan.service` and `garden-regenerate-topics-counts.service` enter systemd `Failed` state on every tick, flooding the warnings tail with FATAL + "Failed to start" pairs that crowd out genuine signal. An absent library corpus is a legitimate un-provisioned state, not an error — the audit/reconcile simply has nothing to do. Change both `die` calls (and the analogous `[ -f "$README" ]` / `[ -d "$LIB/topics" ]` guards on the unattended `--land`/scan path) to a clean no-op: `log` an informational "no library corpus in synced clone; nothing to reconcile/audit" line and `exit 0` (or exit 75, which both units already normalize to a clean skip via `SuccessExitStatus=... 75`). Keep the `die`/exit-2 behavior for the explicit operator-invoked `--library <dir>` path where a missing corpus at an explicitly-named root really is a usage error; only the tip-synced service path should treat absence as a no-op.
